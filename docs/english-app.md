# 英語学習アプリ 引き継ぎメモ

新しいセッションでこのアプリの開発を続けるときは、まずこのファイルを読む。

## 1. コンセプト（すべての設計判断の基軸）

前提: モバイル版での使用を前提に作る。デスクトップは二の次。

1. 単語カードのスワイプと編集。スワイプはページをめくる感覚、編集は絵やメモを書き込む感覚。
2. シンプルすぎるUI/UX × 高度なカスタム機能。表に出す要素は極限まで減らし、ソート・フィルタ・表示項目は深くいじれるようにする。
3. 一人一人の学習方法に合ったカード作成と、スワイプ時の表示/非表示設定。
4. 間違えた回数に応じた重み付け復習。×・△ が多い語ほど復習によく出る（× を特に重く）。
   ※ もともとは「エビングハウスの忘却曲線」だったが、期限方式は実装後にユーザーの判断で撤回した（6章参照）。

## 2. 起動と確認

開発サーバーは `.claude/launch.json` の `english-app`（ポート3200）を preview_start で起動する。Bashで `npm run dev` は使わない。

```bash
npx tsc --noEmit
```

```bash

```

画面は http://localhost:3200/english （ルート `/` もそこへリダイレクトする）。確認は必ずモバイル幅（375×812, resize_window の mobile プリセット）で行う。ページ全体が横スクロールしたらレイアウト崩れとみなす（単語一覧テーブルの内部横スクロールは正常）。

eslint は**既存分として 3 errors / 2 warnings（計5件）が残っている**。これは以前からのもので、自分の変更で件数が増えていなければよい。件数を基準に見ること。

状態は **IndexedDB** の `english-app` / `state` ストア / キー `data` に `{ rev, data }` の形で入っている（旧 localStorage の `english-app-data-v1` は移行後 `-backup` に改名されて残る）。ブラウザのJSから `indexedDB.open("english-app")` で読める。検証でユーザーの学習記録を書き換えたら、必ず元に戻してから終わること。

`window.confirm` はこの環境では何も表示せず false を返す。確認ダイアログの動作確認は `ConfirmButton`（画面内の二段階確認）で行う。

## 5. 設計上の決定と、その理由

- **学習記録は IndexedDB に置く（localStorage は使わない）。** 元は localStorage に丸ごとJSONで入れていたが、カードの背景画像が1枚最大1.2MB（`MAX_IMAGE_CHARS`）入るのに対して **iOS Safari の localStorage は約5MB** しかない。しかも `setItem` を try/catch 無しで呼んでいたので、**溢れた時点で例外が投げっぱなしになり、以後の学習記録が一切保存されなくなる**（画面には何も出ない）。取り返しがつかないデータなので移した。
  - 注意: **Chrome では再現しない。** 実測でこのMacの Chromium は localStorage に30MB書けた（IndexedDB の割当は2.78GB）。**上限が問題になるのは実機の iOS Safari** で、そこが本番。手元で再現しないからといって無いことにしない。
  - 記録は `{ rev, data }` の1レコード。`rev` は書き込みのたびに1つ増える。
  - **書き込みは「読んで、自分の知っている `rev` と同じなら書く」を1つのトランザクションでやる。** ホーム画面のPWAとSafariのタブを同時に開くと、どちらも全体のコピーを持っているので、**後から保存したほうが相手の記録を丸ごと消す**。食い違ったら書かずに諦め、赤い帯で再読み込みを促す。黙って消えるよりよい。
  - **保存はまとめて書く**（`SAVE_DEBOUNCE_MS` = 400ms）。カードは連続でめくるので1回ごとに全体を書くと無駄。ただし**まとめている最中にアプリを閉じられたぶんは失われる**ので、`pagehide` と `visibilitychange`（hidden）で書き切る。iOS はそこから始めた書き込みが必ず終わる保証が無いため、間隔は短くしてある。
  - **失敗は必ず画面に出す**（`onStorageProblem` → EnglishApp の赤い帯）。容量超過 / 別タブとの衝突 / その他の3種で文言を分ける。閉じるボタンは付けない。
  - 帯を出すとヘッダーと本文の間に高さが増えるので、**設定シートの `top`（ヘッダーの高さ61を直に渡している）に帯の実測高さを足す**。文言が2〜3行に折り返すので決め打ちにできない。測るのは `ref` + `useEffect` ではなく **callback ref**。このコンポーネントは読み込み中に早期 return するので、`[]` の `useEffect` は入れ物がまだDOMに無いうちに一度走って終わる。
  - **旧 localStorage のデータは初回に読み込んで移し、元のキーは `-backup` に改名して残す（消さない）。** 改名するのは、IndexedDB がブラウザに追い出されたとき古いスナップショットへ黙って巻き戻るのを防ぐため。手で戻したいときのために中身は取ってある。
    - **`-backup` は自動では絶対に読まない**（`readLegacy()` は `LEGACY_KEY` だけ見る）。ここを `?? getItem(BACKUP)` にすると改名の意味が消え、IndexedDB が空になった瞬間に移行日の記録へ巻き戻って、それ以降の学習記録が消えたまま「昔のデータはある」状態になる。**監査で実際にこの書き方をしていて指摘された。**
  - **退避（fallback）した書き込みには版番号を付ける。** 読みは「IndexedDB → 空なら localStorage」なのに、書きは「IndexedDB → 失敗したら localStorage」に落ちる。番号が無いと、1回書き込みに失敗したセッションのぶんが**次の起動で一度も読まれないまま IndexedDB 側に上書きされて消える**。`loadData` で両方の版番号を比べ、新しいほうを採る。
  - **書き出し / 読み込み（設定 → 学習データ）が唯一のバックアップ手段。** 端末の紛失・機種変更・ブラウザによる退去・「サイトデータを削除」のどれでも記録は消えるし、**Capacitor 版は別オリジンになるので PWA 側の IndexedDB は1件も見えない**（保存先が IndexedDB でも同じ。オリジンが変わる以上どちらでも引き継げない）。ストア申請の前提でもある。読み込みは必ず `normalize()` を通し、版番号を進めてから書く（衝突検知に引っかかって黙って失敗しないように）。
  - IndexedDB が開けない環境（プライベートモードなど）では localStorage へ退避する。容量の問題は残るが、そのときは帯が出る。
  - `navigator.storage.persist()` を起動時に1回頼む。断られても動きは変わらない（localhost では実際に断られた。ホーム画面に追加した端末では通ることが多い）。
- ユーザーの編集は `EnglishData.edits` にオーバーライドとして保存し、DBファイル自体は書き換えない。DBを再生成しても編集が消えないため。
- 単語・文法はAPIを呼ばない。生成待ちが体験を壊すので、事前生成DBから即出題する。
- **初回はチュートリアルを出す**（`EnglishData.tutorialDone`。旧フローを通った既存ユーザーと学習記録のあるユーザーは storage.ts の移行で「済み」扱い）。**2026-08-15 に全面的に作り直した。全24ステップ。**
  - **形はスポットライト**（`Spotlight.tsx`）。画面を暗くして対象を1つだけ抜き、隣に**1行だけ**添える。
    それ以前は説明バナーを画面上部に置いていたが、ユーザーの指摘は「文章が長くて読む気にならない」
    「どこを見ればいいか分からない」の2つで、**どちらも同じ原因**だった。バナーは対象を指せないので
    位置を文章で説明するしかなく（「左上のスライダーが…」）、それが本文を段落まで膨らませていた。
    指せるなら1行で足りる。コピーの総量は約880字 → 約120字になった。
  - **暗い部分はタップを通さない。穴だけが押せる。** これは飾りではなく**進行の仕組みそのもの**で、
    穴の位置がそのまま「次にできる操作」の限定になる。だからデモを「○ボタン → 右スワイプ →
    ×ボタン → 左スワイプ」の4つに割っても、各ステップで意図した操作しかできない
    （ボタンを抜けばスワイプできず、カードを抜けばボタンを押せない）。**入力方法を判別するコードが要らない。**
  - 暗幕は **SVG のマスク**で描く。穴を何個でも開けられるので、離れた2か所を同時に指せる
    （「単語の列」と「下タブの単語リスト」など）。印を `+` でつなぐと合わせて対象にできる。
    タップを吸うのは穴を囲む板で、**根は `pointer-events-none` のまま**にすること。
    根に当たり判定を持たせると全画面なので穴の位置まで吸う（実際これで ○ ボタンが押せなくなった）。
  - **矩形は要素ごとに測り、それぞれ自分を切り取っている枠に収めてから、まとめる。
    まとめるのは同じ印の中だけで、印をまたいではいけない**（`findTargetGroups` が
    `+` ごとのグループを返し、`measureBoxes` がグループ単位で `mergeBoxes` する）。
    表の1列は連続しているので1つの穴に、下タブは別の印なので隣り合っていても別の穴で残る。
    - **以前は測った矩形を全部まとめて統合していて、`col-word+nav-database` の
      ステップが1つの大きな長方形になっていた**（意味の列や他のタブまで抜けた）。
      単語列を切り取っている表のスクロール枠の**下端が下タブの上端とちょうど接している**ため、
      PAD を足した時点で 5px 重なって統合の条件を満たしていた。実機で報告された。
      実DOMでの計測: 列の下端 750.5 / タブの上端 745.5、旧=穴1つ、新=穴2つ。
    余白 (PAD) は**切り取りより前に**足す。逆にすると枠に収めたあとで膨らんで漏れる。
  - **穴の輪郭（青枠）は、穴そのものと違って画面内に丸める。** `outline` は要素の外側に
    描かれるので、カード詳細のように画面幅いっぱいの対象だと左右の辺が画面外に出て
    上下2本しか見えなくなる（実機で報告された）。輪郭の矩形をビューポートで切り、
    `outlineOffset: -2` で内向きに描く。**穴（SVGのマスク）は丸めない。**
    丸めると指している対象の端が暗幕に隠れる。
    **`position: fixed` に行き当たったら切り取りを打ち切る。** fixed は祖先の overflow に切り取られない。
    単語詳細は fixed なのに単語リスト（スクロールコンテナの中）から描かれているので、
    ここで止めないと交差が空になって穴ごと消える。
  - **デモが出ているあいだは、その中の印だけを対象にする**（`data-tour-layer="demo"`）。
    2周目は下の単語タブに本物のカードが出ていて、`answer-known` などの印が2つに当たり、
    その和集合が穴になって位置がずれる。初回は測定前でカードが無いため気づかれなかった。
  - **操作で進むステップに「次へ」は無い。** 望みの操作をした時点で次へ送る。
    読むだけのステップにだけ「次へ」を出す。**「戻る」はチュートリアル全体で出さない**（ユーザーの指定）。
  - **ステップは番号ではなく名前で参照する**（`STEP` 定数）。途中に1つ挟むたびに `EnglishApp` 側の
    `tourStep === 13` のような数字を全部付け替えることになり、実際に何度か取りこぼして挙動が飛んだ。
    いまは数字の直書きがゼロ。

    シール貼る → シールめくる → 学習進捗度3つ → 復習へ → ○× → △の演習 → 設定を開く →
    出題の設定 → スワイプ時オプション → 準備完了。

    **測定のボタンを ○ × の2つに揃えた**（`showUnsure={false}`）。解説は残す。
  - **測定中はボトムナビと歯車を塞ぐ。** 他のステップは板が覆うので勝手に塞がるが、

    アンマウントされて答えた分が消える（docs の既知課題）ので、実質その不具合も塞がった。
  - **チュートリアル中はカード右下の ↑ を出さない**（`VocabTab` の `tourActive`）。
    開くと CardDetailSheet がスポットライトの板の下に潜って操作できなくなり詰む。
  - **シールをめくったら1秒だけ画面を止めて褒める**（`frozen`）。すぐ次へ送ると表が横へスクロールして
    「めくれたのか分からない」ままになる。この間は穴も塞ぎ、スキップも出さない。
  - **復習の説明で学習中の語が1つも無ければサンプルを1枚出す**（`tourSampleReview`）。
    測定10問が全部 ○ だと空画面で詰む。
  - デモカードは `TutorialFlow` 内の固定データ（DB読込を待たない）。`WordCard` / `FlyingCard` /

  - スキップ可。設定（歯車）の「チュートリアル」からいつでも見直せる。

- レベルはユーザーが選ぶのではなく最初の10問で測り、以後は正答率で動的に上下させる。苦手タブの出題語も現在レベルに追随する。
- 測定の10問目に答えた時点で、測ったレベルの最初のキューまで作ってしまう（`onPlacementNext`）。結果画面の「学習をはじめる」は `phase` を `quiz` にするだけ。
  - 以前はここで `idle` に落としていたが、`idle` の画面は「出題できる単語がありません。設定を見直すか、レベルを再測定してください」しか出さないので、測定を終えた直後に行き止まりに突き当たっていた。測定とキュー作成のあいだに `setData` の反映待ちを挟まないよう、レベルは state ではなく測定値 `est` から直接渡す。
  - 測定に使った10語は `pSeen` として除外して積む。測ったばかりの単語がそのまま続けて出ると測定の続きに見えるため。
- `idle` の画面は「出題対象レベルが1つも無い」ときと「レベルはあるが出題できる語が無い」ときで文言とボタンを分ける。前者では `switchMode` がキューを作れず「出題する」ボタンが無反応になるので、測定への導線を出す。
- カード画面の上部タブは出題モードそのもの。**演習**と**復習**の2つだけ。
  - 演習 … 高速に ○ / × へ仕分ける。ボタンは × ○ の2つ、既定では回答後に裏面を見せない。出題は「新出（未学習）」と「既出（学習中＋学習完了）」を `drillNewRatio`（既定50%）で混ぜる。片方の在庫が尽きたらもう片方で埋めるので、比率はあくまで目安。
  - 復習 … 取りこぼした語を覚え直す。ボタンは × △ ○ の3つ、既定では裏面を見せる。出題は**学習進捗度が学習中**のものだけ。
  - タブの件数は `buildQueue` が同じモードで拾う集合と一致させる（復習の件数 = `dbStats().learning`）。片方だけ直すとズレる。演習は無限に出し続けるので件数を出さない。
  - **復習が尽きたかどうかは、キューではなく「タブの件数」で判定する**（`reviewEmpty`）。
    `record()` の `setData` と `next()` は同じティックで走るので、**`next()` が作り直すキューには
    いま答えたぶんがまだ入っていない。** キューを基準にすると、`masterKnownCount` 回目の ○ で
    学習完了になった語がもう1度出てしまい、復習の対象が1語だけのときは延々と出続けたうえ、
    最後にカードが画面に残って操作を受け付けなくなっていた（実機で報告された）。
    件数は毎レンダー `data` から数え直すので、答えた瞬間に 0 になる。
    件数はタグの絞り込みを掛けない**上位集合**なので、0 なら `buildQueue` も必ず空。
    逆向き（件数>0 だがキューが空）はもとの `item` の分岐が拾う。
    チュートリアルが借りるサンプル（`tourSampleReview`）だけは除外する。
  - `next()` は在庫が尽きたときも**必ずキューを入れ替える**。何もせず返すと、答え終わったカードが
    画面に残ったまま操作できなくなる。
  - 更新（↺）とコメント（💬）のボタンは削除した。メモはカード右下の ↑ から詳細を開いて書く。
  - 「解説を飛ばす」は ○ / × だけでなく **△（4択）にも効く**。選択肢を押した時点で正誤も見せずに上へ飛ばす。片方だけ飛ばすと、設定を入れているのに △ で毎回止まる。
- レベルの自動調整（`evaluateLevelShift`）は演習モードの回答だけで判定する。復習は苦手な語に偏るので、数えるとレベルが不当に下がる。
- 出題対象レベルは1つとは限らない。`activeLevels()` が自動設定なら測定値の1つ、手動設定なら選択したぶんすべてを返し、`buildQueue`/`dbStats` は `Level[]` を受け取る。手動設定のあいだは正答率によるレベル自動調整（`evaluateLevelShift`）を走らせない。
- ステータスは**2軸**で持つ。1つに混ぜると「なぜこの語が出るのか」が読めなくなるため分けてある。
  - 前回結果（`LastResult`）… 最後にユーザーが答えた結果そのもの。○ / △ / ×。未回答なら `null` でバッジを描かない。○ を付ければ ○、あとで × を付ければ × に変わるだけで、それ以外の意味は持たせない。
  - 学習進捗度（`Progress`）… 未学習 / 学習中 / 学習完了。**出題の対象はこちらで決める**。
- 学習進捗度の判定は `progressOf()` の1か所だけ。未出題なら未学習、**初見で ○ を出した語**または ○ が `masterKnownCount` 回（既定3）連続した語が学習完了、残りが学習中。
  - **どちらも「前回結果が ○」であることが条件。** あとで △ や × を出したら学習中へ戻る。この条件が無いと、一度学習完了になった語は忘れても永久に学習完了のままで、学習中だけを拾う復習モードに二度と出てこなくなる（実データで12語が該当していた）。
  - 初見の判定に **△→正解 は含めない**。「怪しいが4択は当たった」は身についたとは言えない。以前 `isCorrect(history[0])` にしていたため、前回結果が × なのに学習完了という組み合わせが生まれていた。
  - 連続は `consecutiveKnown()`。△ や × を挟むと数え直す。累計だと一度覚えた語が誤答を挟んでも完了のままになる。
- **学習完了への近道は「履歴に △ も × も一度も無い」ときだけ効く**（`progressOf`）。
  以前は `history[0].r === "known"`、つまり初見が ○ でありさえすれば通していたので、
  そのあと × を何回出しても ○ を1回取るだけで学習完了へ戻り、連続の判定に永久に到達しなかった。
  一度でも外した語は、そこから `masterKnownCount` 回続けて ○ を出すまで学習中に留める。
  副次的に、履歴が直近50件で切られると `history[0]` が本当の初見でなくなる LOW リスクも消えた。
  検算は `scripts/check-english-queue.ts` と、9ケースの手検算（初見○のみ=done / 初見○→×→○=learning など）。
- **1枚のカードに2回答えさせない**（`WordCard` の `answeredRef` / `flownRef`）。
  `step` も `picked` も state なので、素早く連打すると更新が届く前に2回目のハンドラが走り、
  同じ語に2回記録される（「○ を連打すると1枚に ○ が2つ付く」の正体）。ref なら同じフレームでも即座に効く。
  key が「単語#出題連番」なので次のカードでは自動的に戻る。← で取り消したときだけ `answeredRef` を戻す。
  `flownRef` は別の不具合も塞いでいる。裏面の「次へ」を連打すると `onNext` が2回走り、カードを1枚読み飛ばしていた。
- **出題はタグでも絞れる**（`VocabSettings.tagFilter`、`passesTagFilter`）。「単語の設定 → 出題の設定 → タグ」。
  `data.tagProps` から毎回組み立てるので、プロパティの追加・削除にそのまま追随する。
  同じプロパティ内は OR、プロパティ同士は AND（単語リストのフィルタと同じ規則）。
  - **設定シートを閉じたら出題キューを作り直す**（`closeFilter`）。作り直さないと今のバッチを使い切るまで
    前の条件のカードが出続け、タグで絞ったのに条件に合わない語が出てくる。
    「難易度を変えても出題中のキューが切り替わらない」という既知課題も同時に解決している。
- **`Sheet` の閉じるスワイプはネイティブの touch で追跡する。** pointer だけで追っていた頃は
  実機で全く効かなかった。ブラウザがジェスチャをスクロールと判定した瞬間 `pointercancel` で途切れ、
  その判定のスロップ (8〜10px) が閉じるしきい値より小さいので**必ず競争に負ける**
  （`CardDetailSheet` で先に踏んでいた罠と同じ）。`preventDefault` は React の `onTouchMove` では効かないので
  `addEventListener({ passive: false })` が要る。pointer 側はマウス専用に絞る。
- **カード詳細の閉じる ↓ は、見出しブロックと縦の中心を揃える。** ボタンはパネルの拡大に巻き込まれないよう
  transform を持つパネルの外に置いてあるので flex では揃えられない。見出しの高さを callback ref +
  ResizeObserver で実測して自分で合わせる。見出し語は長さで 4xl / 3xl / 2xl の3段に変わり、
  長いイディオムは2行に折り返すので、決め打ちの余白では合わない。
- **興味テーマは読解タブの「出題テーマ」に統合した**（2026-08-15）。設定（歯車）から消し、
  `InterestsEditor.tsx` も削除。**保存先は `settings.interests` のまま**にして既存の記録を残している
  （中身の意味は「ユーザーが追加したテーマ」に読み替え）。
  「おまかせ」は裏で興味テーマを送るのをやめ、**空のまま送ってAIが題材を決める**。
  勉強目的も同じく自分で足せる（`settings.customPurposes`）。**API 側も直すこと。**
  `PURPOSE_PROMPT` に無いキーは既定へ潰れるので、足した目的が生成に一切効かなかった。
  いまはその文字列をそのまま指示に使う。
  - 追加・削除は**「追加・削除」ボタンを押したときだけ**入力欄と × を出す。常設にすると選ぶだけのときに
    邪魔で、選ぼうとして × を踏む事故が起きる。
- **文字の大きさは 2026-08-15 に一段上げた。画面の最小は 9px → 11px。**
  単語リストの本文 13→15px、見出し 11→13px、単語詳細の 12→14px（16か所）、
  カードの発音記号・品詞 12→14px、下タブのラベル 10→11px。

  （どちらも指で押すには小さすぎた）。**入力欄だけは 16px 未満にしない**という決まりは据え置き。
- 色は軸ごとに系統を分ける。前回結果は ○=青（`#4A99EA`）/ △=黄（`yellow-500`）/ ×=赤。学習進捗度は 未学習=白 / 学習中=灰 / 学習完了=黒。
  - 学習進捗度は「進むほど濃くなる」並びだが、この画面は常にダークなので黒が地に沈む。3つとも枠線を持たせて輪郭が出るようにしてある。枠線を外すと学習完了だけ見えなくなる。
- ステータスの表示名・配色・手動指定の有無は `worddb.ts` の `RESULT_BADGE` / `PROGRESS_BADGE` と `statusBadges()` が唯一の定義。カード画面・単語一覧・長文の3か所が同じ関数を通る。以前ここが画面ごとの組み立てになっていて表示が食い違った。
  - `statusBadges()` は **これまでの回答回数**（`counts`: ○=knownCount / △=unsureCount / ×=unknownCount。単語一覧の列と同じ数え方）も返し、カード詳細のステータス欄に「これまでの回答 ○n回 △n回 ×n回」として出す。編集中（手動付け替え）も出しっぱなしにする。実際の記録が横に見えていた方が判断しやすいため。
- 手動でのステータス指定は2軸それぞれに持つ（`resultOverride` / `progressOverride`）。カード詳細で軸ごとに選び、「自動」で外す。そのカードに回答した時点で**両方とも**外れる（記録と食い違ったまま固定されると、タブの件数や出題対象が実態とずれるため）。
- 「学習済みなら出題しない」「初見の○は永久に出さない」「n日で再出現させる」の3つは廃止した（`masterKnownCount` は学習完了の判定にだけ残っている）。裏で分類が変わると自分の回答と表示が食い違い、なぜその語が出るのか分からなくなるため。
- **復習の出題順は「間違えた回数」の重み付けだけで決める**（`worddb.ts` の `reviewWeight()`。復習・演習の既出側の抽選が使う）。
  - 重みは `1 + ×回数×3 + △→誤答×2 + △→正解×1`、さらに直近の結果を上乗せ（前回 × なら +4、前回 △ なら +2）。× を特に重く、というユーザーの指定。
  - 4択で当てた回数（`correctCount`）も加点する。「怪しい」と自己申告した証拠だから。
  - 復習の対象は今までどおり**学習進捗度が学習中のものだけ**。件数も `stats.learning` のまま。
  - 数字を変えたら `scripts/check-english-queue.ts` の検算も合わせて直す（重みの単調性と、×多い語が実際に先に出る割合を大数で確かめている）。
- 読み上げはブラウザ内蔵の Web Speech API だけで作る。追加のキーも費用も要らず、認証の無い公開URLを他人に使われても請求が増えないため（**Anthropic API には音声が無い**ので、クラウドTTSを使うなら別プロバイダの契約が要る）。差し替えるときは `lib/english/speech.ts` の中だけを直す。
  - iOS Safari の罠が2つある。**最初の `speak` はユーザー操作の中から呼ばないと無音になる**ので、カードに触れた時点で `primeSpeech()`（音量0の空発話）を1回通して解錠する。`getVoices()` は非同期で初回だけ空配列を返すので `voiceschanged` を待って選び直す。声が選べていなくても `lang` は必ず英語にする（指定しないと端末の既定言語で読まれ、英単語がローマ字読みになる）。
  - **音声は名前で選ぶ（`PREFERRED_VOICES`）。「en-US の先頭」を取ってはいけない。** macOS には Albert / Bad News / Bahh / Boing …といったジョーク音声が en-US として入っていて、しかもアルファベット順で先頭に来る。実測（macOS Chrome）では英語の音声180件中 en-US が28件あり、そのうち `default` が立っているものは**1つも無かった**（`default` は Kyoko(ja-JP) だけ）。素直に先頭を取ると **Albert** が選ばれ、単語をふざけた声で読む。`localService` も全部 true で区別に使えない。実際にこの実装で一度そうなった（修正後は Samantha が選ばれる）。
  - 選ぶ順は 1. `PREFERRED_VOICES` の並び順（同名が複数あれば en-US 優先）→ 2. 端末の既定が英語ならそれ → 3. `NOVELTY_VOICES` を除いた中から en-US → en-GB → 先頭。
  - 単語リストの各行にもスピーカーを置く（単語の横）。行のクリックはカード詳細を開くので `stopPropagation()` する。シールを貼った列ではセルごと隠れ、めくれば押せる。単語列は**2行構成**（1行目: 単語＋スピーカー、2行目: 品詞・レベル。ユーザー指定。セルが高くなるのは許容）。
  - **速さは `speech.ts` のモジュール変数が1つ持ち、`EnglishApp` から `setSpeechRate()` で同期する。** 読み上げを持つ画面が4つ（カード・カード詳細・単語リスト・長文）あり、prop で配ると渡し忘れた画面だけ既定に戻る。
  - **`primeSpeech()` は `answer()` と `openChoices()` の中でも呼ぶ。** 下部の × △ ○ ボタンはカード本体の外にある兄弟要素なので、ボタンだけで仕分けているとカードの `onPointerDown` を一度も通らない。演習は「× ○ の2ボタンで高速に仕分ける」のが本来の使い方なので、これが例外ではなく主経路。カードに触れない限り解錠されず、iOS では自動読み上げが永久に無音になる。
  - `speak()` は必ず前の発話を `cancel()` してから始める。止めないとカードを続けてめくったとき読み上げが順番待ちで溜まる。
  - **飛んでいくコピー（ghost）では読み上げない。** 本体で既に読んでいるので二重になる（振動と同じ扱い）。コピーの unmount で `stopSpeaking()` を呼ぶのも禁止。コピーは飛び終えた直後 (EXIT_MS+80ms) に片付くので、その頃には手前に出ている次のカードの読み上げを切ってしまう。
- **オフライン対応は Service Worker（`public/english-sw.js`）で行う。** ワークボックス等のライブラリは入れない（キャッシュの分け方が上の4種類だけで、生成される設定を読むより直接書いたほうが短い）。
  - **スコープは `/english` だけに絞る。** 同じオリジンに `/`（EDINET分析）・`/tasks`・`/midterm`・`/analyze` が同居していて、それらまで巻き込みたくない。
    - スクリプトは `public/` 直下（= `/english-sw.js`）に置き、登録側で `{ scope: "/english" }` を渡す。スクリプトの位置より**深い**スコープは自由に指定できる。
    - **`public/english/sw.js` に置く手は使えない。** そこに置くとスコープが `/english/`（末尾スラッシュ付き）になり、ページのURLである `/english` が前方一致しないので、肝心のページが管理下に入らない。
    - スコープが絞られていても、**管理下に入ったページからの fetch は URL がスコープ外でも全部 SW を通る**。だから `/english-words/*.json`（スコープ外）もキャッシュできる。
  - **最重要の不変条件: HTMLは、それが読み込むチャンクを全部キャッシュできたときだけ採用する**（`adoptShell()`）。HTMLとチャンクは別のキャッシュに入っているので、素直に書くと**一度も成立したことのない組み合わせ**（新しいHTML＋古いチャンク）がキャッシュに残る。そうなると次にオフラインで起動したとき、HTMLは出るがスクリプトが1つも読めず、SSRの「読み込み中...」から**永久に動かない**（オンラインに戻るまで自力で直らない）。
    - 起きうる筋書きは2つ。(1) 新しい版をデプロイ → オンラインで開く → 小さいHTMLは3秒以内に届いて採用される → 大きいチャンクを取っている途中で画面を消す／トンネルに入る → 次の起動が圏外。**回線が細いときほど起きやすい。** (2) install で HTML だけ先に取っていた頃は、**初回訪問の直後に圏外へ出ただけ**で同じ状態になった（多エージェントのレビューで実際に再現した）。
    - 実装は `STATIC_REF` で HTML から `src=` / `href=` の `/_next/static/...` を拾い、**全部 `english-assets-*` に入れてから**HTMLを `english-shell-*` に入れる。1つでも取れなければ**シェルを更新しない**（今オンラインなのでページ自体はネットワークから出ている。前の「揃った組み合わせ」を残すほうが安全）。既にキャッシュにあるURLは飛ばすので、2回目以降の起動で取り直しは起きない。
    - Next.js は起動に要るチャンクをすべて `<script src>` と `<link href>` に書き出すので属性値だけ見れば足りる。**`next/dynamic` や `React.lazy` を使い始めたらここも直すこと**（遅れて要求されるチャンクは拾えない）。
  - キャッシュは4本立て。
    1. シェル（`english-shell-*`）… `/english` のHTML・`/manifest.webmanifest`・アイコン。**install で先に取る**ので、初回訪問の直後に圏外へ出てもホーム画面から起動できる。アイコン類は `cache.addAll` だと1件の失敗で全部巻き戻るので1件ずつ入れる。HTMLだけは上の `adoptShell` を通す。
    2. `/_next/static/*`（`english-assets-*`）… ハッシュ付きで中身が変わらないのでキャッシュ優先、問い合わせ無し。`adoptShell` もここへ入れる。
    3. 単語・イディオム・文法の静的JSON（`english-data-*`）… **キャッシュ優先で再検証しない。** 合計 gzip 1.25MB あり、起動のたびに再検証させるとモバイル回線で無駄になる。**更新は `DATA_VERSION` を上げて丸ごと入れ替える（DBを再生成したら必ず上げる）。**
    4. 画面遷移（HTML）… ネットワーク優先、3秒で諦めてキャッシュへ落とす。オンラインなら必ず最新のHTMLが出る。
  - `/api/english/*` はキャッシュせず、**圏外のときだけ `{ error: "オフラインです…" }` を 503 で返す。** 呼び出し側は既に `json.error` を読むので、これだけで「Failed to fetch」が画面に出なくなる。POST も通す（GETだけ扱う分岐より前に置くこと）。
  - **キャッシュへの書き込みは必ず `event.waitUntil` に載せる**（`keepAlive()`）。`respondWith` はレスポンスを返した時点で解決するので、載せずに投げっぱなしにするとブラウザが SW を止めたときに書き込みが取り消される。単語DBは1件2〜4MBあり書き終わるまでが長いので、ここは実際に危ない。
  - `?_rsc=` が付いたリクエスト（App Router のクライアント遷移）は素通しする。HTMLとして扱うと壊れる。
  - install で `skipWaiting()`、activate で `clients.claim()`。**claim しないと初回訪問中に読み込む単語DBが1件もキャッシュされない**（初回は登録が終わる前にページの読み込みが始まっている）。飛んでくる版が入れ替わっても `/_next/static` はハッシュごとに別々に残るので、開いたままのページが読み込み済みのチャンクを失うことはない。
  - **開発中は登録しない**（`ServiceWorkerRegistrar` が `NODE_ENV` を見る）。`next dev` の `/_next/static` はハッシュが固定されずHMRも走るので、キャッシュ優先で掴むと更新が反映されなくなる。さらに、本番ビルドを localhost で動かして登録が残ったまま `next dev` に戻ると同じ罠を踏むので、開発時は逆に**登録を外しにいく**。
  - **オフラインで使えるのは「一度オンラインで開いた教材」だけ。** 単語DBは起動時に読むので自動的に入るが、**イディオムと文法は、そのタブを一度開くまでキャッシュに入らない**。入っていない状態で開くと `requestErrorMessage` が「オフラインです…」を出す。事前にまとめて落とす仕組みは、7章Bのレベル別ダウンロードと同じ話なのでそちらでまとめて作る。
- **ヘッダーの上端はセーフエリアに合わせて伸ばす**（`paddingTop: max(0.75rem, env(safe-area-inset-top))`）。ホーム画面から起動すると `status-bar-style: black-translucent` と `viewportFit: cover` の組み合わせで中身がステータスバーの下まで広がるので、足さないと Dynamic Island 機（inset 59px）やノッチ機（47px）で題名と歯車が時計に潜る。
  - **ヘッダーの上に `fixed` で被さるものは、この逃げを一切継がない。自分で避ける。**
    チュートリアルの全画面3層（`TutorialWelcome` / デモ / `TutorialOverlay`）がこれを忘れていて、
    「チュートリアル n / N」とスキップが時計と Dynamic Island に潜っていた（実機で報告された）。
    いまは `TutorialFlow.tsx` の `FULL_LAYER_SAFE` が上下ともまとめて逃がしている。
  - **セーフエリアの不具合はブラウザのタブでは絶対に再現しない。** 上下にブラウザのUIがあるぶん
    インセットが 0 になるため。**ホーム画面に追加して起動しないと出ない。**
    手元で見るときは、対象の層の `paddingTop` を 59px（Dynamic Island 相当）に上書きすると
    実機の見え方を再現できる。
  - **設定シートの `top` も同じ式にする。** シートは `fixed` でヘッダーの高さを直に受け取るので、ヘッダーだけ伸ばすと重なる。`calc(49px + max(0.75rem, env(safe-area-inset-top)) + 帯の高さ)`。61 という数字はこの計算（49 + 12）が畳まれたものだった。実測でインセット0の環境では 61px に解決し、ヘッダーの下端とぴったり一致する。
- **`claude-opus-5` は `thinking` を省略すると adaptive thinking が既定で走り、その思考トークンも `max_tokens` に含まれる**（Opus 4.8/4.7 は省略＝思考なしだったので、そのつもりの値だと足りない）。AI会話の返信は 1024 だったため、会話量「長め」や履歴が伸びたときに思考で使い切って、途中で切れた返信や空文字が HTTP 200 で返っていた。
  - 上限を 4000 に上げ、短い雑談に見合うよう `output_config: { effort: "low" }` を付けた。**`thinking: disabled` は選ばない**。opus-5 で思考を切ると「ツール呼び出しが本文に混ざる」「`<thinking>` タグが漏れる」という既知の失敗があり、effort を下げるほうが安全で費用もほぼ同じだけ下がる。
  - `stop_reason === "max_tokens"` と空文字も失敗として扱う（`generateJson` と揃えた）。見ていないと、切れた返信が成功として画面に出る。
- **AI会話に送る履歴は、後ろから切ったあと先頭が `user` になるまで捨てる。** APIは先頭が user でないと 400 になる。`slice(-20)` は先頭が assistant になることがあり、失敗した回は assistant の返信が増えないので長さの偶奇が変わらず、**以後ずっと同じ形で切り出されてAI会話タブが恒久的に壊れる**（会話をリセットするまで直らない）。
- **`WordCard` の key は `単語#出題連番`。** 語だけだと、復習の対象が1語しか無いとき（測定10問で1問だけ×だった直後など）にキューが `[a]` のまま作り直され、key が変わらないのでカードが解説面のまま固まって先へ進めなくなる。
- **カード詳細の見出し語はカード表面と同じ `text-4xl` を基準にする**（`headwordSize()`）。詳細はカードから開くので、同じ語がそこで小さくなるのはおかしい（以前は `text-2xl` で一段縮んでいた）。ただし見出し語はイディオムを含み最長37文字（"give someone the benefit of the doubt"）で、全部 4xl にすると3行に折り返して sticky なヘッダーが画面を食う。**12文字以下=4xl / 20文字以下=3xl / それ以上=2xl** の3段にする。7,633件のうち約6,000件は10文字以下なので、大半は最大サイズのまま。
- **タグは「プロパティ」の集まりで、ユーザーが自由に足せる**（`TagProp` / `EnglishData.tagProps`）。「試験 / 分野 / テーマ」も**同じ仕組みに載せてある**（`DEFAULT_TAG_PROPS`）。分けたままだと追加・削除・フィルタをそれぞれ2通り書くことになる。
  - **選択はすべて複数選択**（ユーザーの指定）。1単語に「大好き」と「嫌い」を同時に付けられてしまうが、試験タグのように複数当てはまるものと揃えた。プロパティごとに単一選択を選べる案は採らなかった。
  - `builtin: true` は**単語DBの同名フィールド**（`exams` / `domains` / `themes`）から値を読む印。値の読み出しは `tagValuesOf()` の1か所だけで、優先順は **ユーザーの編集 (`WordEdit.tags`) → 旧形式の編集 → DBの値**。
  - **組み込みを削除してもDBの値には触らない。** 消えるのは定義だけ。ただし**名前で作り直しても別IDの空プロパティになる**ので、編集画面に「消した組み込みプロパティを戻す」（↺）を置いてある。これが無いと、うっかり試験を消した時点で7,633語ぶんのタグに二度と手が届かなくなる。
  - **プロパティのIDは表示名と切り離す**（`p_xxxxxxxx`）。名前を変えても、付けたタグが外れない。
  - **プロパティの追加・削除と選択肢の追加は、単語の「保存」を待たずその場で反映する。** 全単語で共通の設定であって、その単語の下書きではないため。値の選択だけが下書き。
  - **保存は既存の `tags` に重ねて書く**（`{...prevTags, ...dTags}`）。下書きは編集を開いた時点の `tagProps` で作るので、編集中に戻した／足したプロパティのキーが下書きに無く、丸ごと置き換えるとそのプロパティの値が消える（実際に一度そうなった）。戻すボタンと追加ボタンも、押した時点で下書きに値を入れる。
- **単語リストのフィルタはタグに対応し、`data.tagProps` から毎回組み立てる**（プロパティの追加・削除にそのまま追随する）。同じプロパティ内は OR、プロパティ同士は AND。
  - あわせて「単語を含む」「意味を含む」「最終閲覧」の3つはフィルタから削除した（ユーザーの指定）。単語・意味は検索パネル側で引けるので重複していた。
- **単語の設定は「出題カードのフィルタリング」と「スワイプ時オプション」の2つに分ける**（`CardFilterSheet`）。以前は `section` を7つ縦に並べただけで、**どれが出るカードを変える設定でどれが見え方の設定か読めなかった**。分類の基準は「出題される集合が変わるか / 変わらないか」の一点。
  - 中は `Collapsible`（文法・読解タブと同じ部品）の入れ子。閉じたままでも今の値が見出しの右に1行で出る。
  - **単語レベルの表示と再測定は歯車から「難易度 (レベル)」の中へ移した。** 難易度の設定と同じ場所にあるほうが探しやすい。歯車に残るのは興味テーマ（読解とAI会話が使うもので、カードとは無関係）だけ。

    1. pointer イベントはブラウザがジェスチャをスクロールと判定した瞬間 `pointercancel` で途切れる。その判定のスロップ（8〜10px）はこちらの発動しきい値（14px）より小さいので、**pointer 追跡は競争に必ず負ける**。最初の実装（pointer のみ）はこれで実機で全く効かなかった。`touchmove` はスクロールが始まっても配送され続ける。
    2. `preventDefault` は React の `onTouchMove` では効かない（React はルートに passive で付ける）。`ref` + `addEventListener({ passive: false })` が必須。
  - `preventDefault` は「先頭から下向きに動いている」あいだずっと呼ぶ。先頭にいる以上、下向きの引きで動かせるスクロールは存在しないので正当なスクロールを殺すことはない。上向き（dy < 0）は止めず、ふつうのスクロールに返す。

  `CardDetailSheet` の根は `fixed inset-0 mx-auto max-w-2xl`。その中の閉じるボタンと回答バーは
  パネルの拡大に巻き込まれないようパネルの外に置いてあるが、**そこを `fixed` にすると
  実機の iOS で描画が壊れる**。根が既にビューポート全面かつ列幅なので、
  `absolute` にしても位置と大きさは1pxも変わらない（375px と 1280px の両方で

    同じ根の中にあり同じ y をまたぐのに、白文字の明るさは境界の上下で変わらなかった
    （見出し 254 / 例文 251 / 派生語 250）。**壊れるのは `fixed` の要素だけ**と分かる。
    iOS は `position: fixed` をビューポート基準の別レイヤーへ持ち上げるので、
    その層が外側のスクロールコンテナの層をまたぐところで合成の継ぎ目ができる。

- **iOS シミュレータを自分で操作できる。** `mcp__Claude_Code_iOS_Simulator__control` で
  `open_url` / `tap` / `swipe` / `screenshot` ができる。**ホーム画面への追加も通しでやれる**
  （共有シート → ホーム画面に追加 → 起動）。実機でしか出ない類の不具合は、まずここで
  再現するかを見ると「実機固有か否か」が切り分けられる。

- **スクショは目視せず画素で測る。** 「見た目が変」の報告は、画素を測ると原因が一段深く分かる

  尺度を較正してから測ること。** 端末幅を仮定すると外す。
- **端末でしか分からない値は、アプリに出させる。** `LayoutProbe` のように
  `innerHeight` / `visualViewport` / `env()` の解決値 / 要素の矩形を画面に出して
  スクショを1枚もらうのが、推測を重ねるより速い。`env()` は JS から直接読めないので、
  `padding-top: env(...)` を当てた要素を作って `getComputedStyle` で読む。
- **セーフエリア関係はブラウザのタブでは絶対に再現しない。** 上下にブラウザのUIがあって
  インセットが 0 になるため。手元で見るときは対象要素の `paddingTop` を 59px に上書きすると
  実機の見え方を再現できる。
- **ライトモードの不具合はプレビューをライト配色に切り替えないと再現しない。**
  `resize_window` の `colorScheme: "light"`。一度これで「修正済み」と誤判定した。
- **チュートリアルの通し確認は別オリジンで。** 作業ツリーをスクラッチパッドに写して
  `next dev -p 3101` を上げると IndexedDB も別になり、真っさらな初回状態を何度でも作れる。
  `localhost:3100` の学習記録に触らない。`node_modules` は `cp -al`。
- **このリポジトリの `/` は EDINET の企業分析ツール。** `preview_start` はサーバーのルートで
  ペインを開くので、必ず `/english` を付けて開く。
- **合成イベントでオーバーレイ越しに操作すると、下の本物のUIに当たる。**

#### B. 単語の拡張 — **2026-08-17 に実施済み（7,633 → 10,604語）**

> 下の見積もりは拡充**前**に測ったもので、結論（データ量は律速にならない）は変わらない。
> 実際に 10,604 語まで増やしても体感は変わらなかった。
> **やり方は5章「語彙の拡充」「レベルは足せる」に集約してある。**
> 残っているのは **C2 の文法問題**（まだ0問）と、さらに上のレベルを足すこと。


**実測済みの結論: データ量そのものは律速にならない。** 以下はこのMacでの実測値で、
すべて語数に線形。スマホは概ね3〜4倍遅いと見る。

| 語数 | gzip | JSON.parse | 索引 | 単語リストの並べ替え |
|---|---|---|---|---|
| 7,633（現在） | 1.25 MB | 11 ms | 5 ms | 3 ms |
| 30,532（4倍） | 約5 MB | 28 ms | 4 ms | 7 ms |
| 76,330（10倍） | 約12 MB | 72 ms | 8 ms | 18 ms |
| 152,660（20倍） | 約25 MB | 153 ms | 14 ms | — |

**3〜4倍（2.5〜3万語）までは何も手を入れずにいける。** 実際の上限は3つ:

1. **メモリ**（最初の天井）。展開後はおよそ生データの2〜3倍。全レベルを一度に読む
   いまの作りだと **10〜15倍（8〜11万語）が実用上の壁**。iOS Safari は
   200〜400MBでタブを落とす。レベル別読み込みにすればこの壁は消える。
2. **単語リストの並べ替え**（一番危ない）。コストは語数ではなく
   **フィルタを通過した行数**に比例する。76,330語でも既定フィルタ（学習中・学習完了）
   なら18ms だが、**フィルタを「すべて」にすると310ms**（Macで。実機は1秒近く）。
   しかも**検索ボックスの1文字ごとに走る**。デバウンスが要る。
3. ~~**転送**~~。**Service Worker で解決済み（2026-08-13）。** 静的JSONは
   `english-data-*` にキャッシュ優先で入り、再検証しない。以前は
   `cache-control: max-age=0, must-revalidate` で起動のたびに10ファイルの
   再検証が走っていた。残るのは**初回だけ**の転送量なので、下のレベル別
   ダウンロードはそのぶん効きが分かりやすくなった。

**レベル別ダウンロードを入れるなら**、以下3か所が「レベルをまたぐ前提」なので必ず対処する:

- **レベル測定**。`samplePlacementWord(dbs, LEVEL_ORDER[pLadder], …)` が A1〜C1 を
  階段状に行き来する。測定前はどのレベルを落とすべきか分からない鶏と卵。
  → 測定専用の小さいファイル（各レベル30語 ≈ gzip 25KB）を常に同梱するのが素直。
- **復習が語を黙って捨てる**。`buildQueue` は `index.get(entry.word)` が空振りすると
  `continue` する。A2で覚えた語がB1へ上がった後で復習から消え、タブの件数もずれる。
  → **`VocabEntry.level` に学習時のレベルが保存済み**なので、
  「出題対象レベル ∪ `data.vocab` に出てくるレベル」を読めばよい。新規は1レベル、
  長く使っても2〜3レベル。新しい索引ファイルは不要。
- **単語リストの既定が「全レベル」**（`useState<LevelFilter>("all")`）。
  → 既定を「ダウンロード済みのみ」にし、未取得レベルにダウンロードボタンを出す。
- （おまけ）レベル自動調整で未取得レベルへ移ることがある。キューの作り直しは
  同期処理なので、そこに取得の待ちを挟む必要がある。

効果: 新規のB1ユーザーなら 1,251KB → **253KB（80%削減）**。
10倍に増やしても1レベルあたり約2.5MBなので、ユーザーが払うコストは今の2倍程度で済む。

**推奨順**: ~~Service Worker~~（済）→ 測定用ファイルの切り出し → レベル別ダウンロード。

レベル別ダウンロードを作るときは、**Service Worker の `english-data-*` キャッシュと
役割が重なる**点に注意する。SW は「一度読んだものが次から速い」だけで、
**まだ読んでいないレベルを先回りして落とすことはしない**。
「このレベルを端末に保存する」ボタンは、SW経由で `fetch` すればそのまま
`english-data-*` に入るので、別の保存先を作る必要はない。
イディオムと文法がタブを開くまでキャッシュに入らない件（5章）も、同じ仕組みで一緒に片付く。

### 検証のやり方（過去のセッションで効いた手順。上の「検証のやり方」も見ること）

- **Service Worker は `next dev` では確かめられない**（そもそも登録しない作りにしてある）。
  本番ビルドを動かす必要があるが、`next build` は `.next` を書き換えるので、
  **他のセッションの開発サーバーが動いているときに同じディレクトリでやってはいけない**。
  スクラッチパッドに作業ツリーを丸ごと写して、そこでビルドして `next start` すればよい。
  - `node_modules` は**シンボリックリンクだと Turbopack が
    「Symlink points out of the filesystem root」で落ちる。** `cp -al`（ハードリンク）にする。
    `/private/tmp` も `/Users` も同じ APFS ボリュームなので数秒で終わる
    （`.bin` の symlink に対する `chflags` だけがエラーを出すが、リンク自体は張れているので無視してよい）。
  - `.claude/launch.json` に `sh -c "cd <写した先> && exec npx next start -p 3210"` の
    エントリを足して preview_start で起動する。**この行はコミットしないこと**（パスがセッション固有）。
  - オフラインの検証は preview_stop で**サーバーを止める**のが一番確実。
    ブラウザの throttle を使うより、キャッシュから返っていることがはっきりする。
  - `next start` は `public/` をリクエストのたびにディスクから読むので、
    SW だけを直すならビルドし直さずファイルを差し替えるだけでよい。
- **ブラウザペインが隠れていると `computer` のクリックが届かない**（30秒でタイムアウトし、
  しかも入力が入らない）。ボタンを押したいだけなら `javascript_tool` から
  `element.click()` を呼ぶ。React の `onClick` はこれで発火する。
  なお下タブのボタンの `textContent` は太字ぶんの不可視コピーがあるので「文法文法」のように
  2回繰り返しになる（5章の末尾）。完全一致で探すときの罠。
- **`respondWith` が解決した直後にキャッシュを数えると、まだ書き込みが終わっていない。**
  実際に「5件入れたのに5件のまま」を見て一瞬バグを疑った。数える前に待つこと
  （そして SW 側は `event.waitUntil` に載せること）。
- **キャッシュの検証は「件数」ではなく「不変条件」で見る。** 件数だけ見ていたら
  HTMLとチャンクの不整合（5章の `adoptShell`）を見落としていた。
  シェルのHTMLを取り出して `/_next/static` の参照を数え、その全部が
  `english-assets-*` にあるかを突き合わせると、壊れた組み合わせが一発で分かる。
  ブラウザのJSから Cache API を直接叩けるので、SW を触らずに測れる。
- **SW経由で来たかどうかは、DevTools のネットワークログでは分からない**
  （キャッシュから返した分も記録される）。`transferSize` / `workerStart` も当てにならなかった。
  一番確実なのは **preview_stop でサーバーを止めて、それでも動くかを見る**こと。
- 画面の確認は必ずモバイル幅（375×812）。`resize_window` の `colorScheme` を light にして、
  端末がライトモードでもダークのままかを見る。
- **そもそも学習記録に触らずに済ませる。** カードやボタンを叩かなくても、
  `body` に検証用の要素を挿してクラスやスタイルを当てれば、アニメーションも配色も測れる。
  飛行の計測は 343×600 の `div` に `card-fly-right` を当てて `DOMMatrixReadOnly` で四隅を出した。
  カードの地色は「白地 + `backgroundImage` の重ね」という実物と同じ組み立てで並べて撮り比べた。
- どうしても回答が要るときだけ localStorage を退避し、終わったら必ず戻す。
  ただし**ブラウザペインはユーザーも触れる**。退避してから戻すまでのあいだにユーザーが
  カードに答えていると、戻した瞬間にその操作を巻き戻してしまう。
  戻す前に退避時点との差分を必ず確認すること（実際に、退避後に5件の回答が増えていた）。
- **合成 PointerEvent は `setPointerCapture` で例外になり、WordCard のスワイプが始まらない。**
  実在しない pointerId を渡すと throw するため（実指では起きない）。検証時は
  `Element.prototype.setPointerCapture` を try/catch で包むパッチを当ててから dispatch する。
  これを知らずに「影が赤い」を静的な地色 (26px 2px) だけ見て検証済みと誤認しかけた。
  ドラッグ中の影は swipeShadow でぼかし・広がりが動く (35px 4.5px など) ので、値の形で区別する。
- **ジェスチャ（ドラッグ・スワイプ）の検証は合成イベントでは不十分。** `dispatchEvent` で作った
  PointerEvent はブラウザのジェスチャ認識（スクロール判定 → pointercancel）を通らないので、
  「合成では動くのに実機で全く効かない」を実際にやった。`computer` の `left_click_drag`
  （モバイルプリセットはマウスをタッチに変換する）で**実入力**を通すこと。
  ツールが30秒でタイムアウト表示になっても入力自体は届いていることがあるので、
  結果は画面の状態で判定する。
- アニメーションの検証は目視ではなく計測で行う。`getComputedStyle` を数十msごとに読む、
  `DOMMatrixReadOnly` で四隅を出す、`animationPlayState='paused'` で止めて撮る、など。
  **ブラウザペインが非表示だと rAF とCSSアニメーションが止まる**ので、
  計測前にスクリーンショットを撮ってペインを表示させておくこと（これで一度、
  ゴーストが早期に消えたように見える誤計測をした）。
- 借りている開発サーバーは `app/globals.css` の再ビルドが数分遅れることがある。
  CSSを触ったら**配信中のCSSを直接見る**か、`npx next build` の出力を確認する。
  最小化で `0.75s` が `.75s` になる点に注意（grep が外れる）。
  - **開発サーバーが動いているあいだに `git stash` しない。** サーバーが stash 中の
    HEAD 版を掴んだまま戻ってこなくなる（`touch` しても再ビルドされなかった）。
    eslint の基準値を取りたいだけなら、stash ではなく `git show HEAD:path` を使う。
  - CSS が配信に反映されないときは、同じ内容の `<style>` をページに挿して測ればよい。
    測っているのは自分が書いたCSSそのものなので、ビルド経路の遅れとは切り分けられる。
    そのうえで `npx next build` の成果物を grep して、本番の値が合っているかを別途確かめる。
- eslint の基準値はリポジトリで違う。claudecode 側は6件（`components/tasks/TaskApp.tsx` を含む）、
  デプロイ用リポジトリ側は5件。件数だけを見て「増えていないか」で判断する。
- 単語DBを触ったら、全レベルを走査して「見出し語の非ASCII混入ゼロ」「重複ゼロ」
  「`count` と `words.length` の一致」を確認する。JSONは `JSON.stringify(j, null, 1)` で
  バイト単位の往復が取れるので、スクリプトで書き換えても差分は変更箇所だけになる。
- 出題キューや復習間隔のような**純粋なロジックは画面を触らずに検算する**。
  `scripts/check-english-schedule.ts` のように単体でコンパイルして走らせればよい
  （テスト基盤は無い。コマンドはそのファイルの冒頭にある）。
  合成データで「タブの件数」と「`buildQueue` が実際に拾う語の集合」を突き合わせられるので、
  画面を操作して学習記録を汚す必要がない。
- **ブラウザのAPIに頼る機能は、必ず実際の端末で値を出して確かめる。**
  読み上げの音声選びはこれで不具合が見つかった（`getVoices()` の中身を数えたら、
  en-US に `default` が1つも無く、先頭がジョーク音声だった）。
  「たぶんこう動く」で済ませず、`getVoices()` の一覧のように**実際の値を出力して見る**こと。
